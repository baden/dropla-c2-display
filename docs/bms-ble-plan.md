# Прямое подключение дисплея к BMS по BLE — идея на будущее

| | |
|---|---|
| Статус | **Идея / план. Не реализовано.** |
| Дата | 2026-10-26 |
| Железо | Waveshare ESP32-S3-Touch-LCD-1.85 + JK-PB2A16S-30P |
| Проверено | BMS рекламируется (`A4:C1:38:05:47:C3`, −70 dBm); архивный realtime-запись декодирована |
| Не проверено | BLE central на самом дисплее, дальность с места установки, расход RAM, совместимость NimBLE с Arduino core 3.3.12 |

Связанные документы: [`JK_BMS_BLE_Protocol.md`](JK_BMS_BLE_Protocol.md),
[`JK_BMS_CAN_Integration.md`](JK_BMS_CAN_Integration.md), утилита
[`../tools/ble_scan.py`](../tools/ble_scan.py).

---

## 1. Короткий ответ

**Да, технически дисплей может сам подключиться к BMS и читать напряжение.**
ESP32-S3 поддерживает BLE 5.0 и роль central; BMS отдаёт напряжение пакета в
realtime-записи (offset 150). На архивном запросе значение сходится:
57 667 мВ → на экране `57.7`.

Но это не обязательно лучший путь:

- в проекте уже описан канал **BMS → CAN → хост → USB → дисплей**
  ([`JK_BMS_CAN_Integration.md`](JK_BMS_CAN_Integration.md)); если CAN на машине
  будет, отдельный BLE-канал — дублирование;
- дисплей всё равно питается по USB, поэтому «прямой BLE» даёт автономность
  **по данным**, а не по питанию;
- BMS пускает только **одного central**: пока дисплей подключён, приложение JK
  на телефоне не подключится, и наоборот.

Прямой BLE оправдан, если: нет CAN-адаптера/проводки, нужен автономный стенд,
или напряжение должно оставаться на экране при падении/перезапуске хоста.

---

## 2. Что требует протокол

| Требование | Следствие |
|---|---|
| Сервис `FFE0`, characteristic `FFE1` (`notify` + `write-without-response`) | Все запросы пишем в `FFE1`, уведомления слушаем там же |
| Один central | Конфликт с телефонным приложением JK; реклама пропадает, пока кто-то подключён |
| BMS не стримит | Нужен опрос `0x96` раз в секунду; без запроса данных нет |
| Сначала `0x97`, затем `0x96` | На «холодном» соединении без `0x97` могут прийти только settings-записи |
| Ответ — 300 байт | При MTU 247 это два notify (244 + 56 байт) |
| `AT\r\n` в потоке | Фильтровать 4-байтовые пакеты `41 54 0D 0A` |
| CRC — сумма байт | `sum(rec[0..298]) & 0xFF == rec[299]` |
| 32-slot layout | Напряжение пакета — `u32` по offset **150**, SOC — байт **173** |
| ~1.0–1.2 с на ответ | 1 Гц — стабильный режим, чаще не нужно |
| Сопряжение не требуется | PIN `1234` и пароль настроек `123456` — не логировать |

Формула для текущего UI:

```text
voltage_cv = (pack_mv + 5) / 10     // 57667 мВ → 5767 → "57.7"
batt_pct   = soc                    // 100 → "100%"
```

## 3. Проверка декодирования

Архивный realtime-запись из [`JK_BMS_BLE_Protocol.md`](JK_BMS_BLE_Protocol.md)
(299 байт в документе: один нулевой байт потерян в неразобранном хвосте, CRC при
этом сходится):

| Поле | Значение |
|---|---|
| Напряжение пакета | 57 667 мВ (57.667 В) → `5767` сВ → `57.7` |
| SOC | 100 % |
| Ячейки 1…16 | 3604, 3609, 3601, 3605, 3603, 3604, 3606, 3603, … мВ |
| Delta / min / max | 8 мВ; 3601 (№3) / 3609 (№2) |
| T1 / T2 | 21.1 / 21.4 °C |
| MOSFET заряд/разряд | оба включены |
| CRC | `sum(bytes[:-1]) & 0xFF == bytes[-1]` — сходится |

На реальном проводе запись будет 300 байт. Парсер должен принимать ровно 300
байт и проверять документированные offsets; архивный вектор использовать только
для проверки полей, а не длины.

## 4. Варианты архитектуры

| Вариант | Кто central | Плюсы | Минусы |
|---|---|---|---|
| **A. Дисплей → BMS** | ESP32-S3 | Без хоста и донгла; напряжение живёт при падении хоста; радио уже есть | Занимает единственный central; дальность зависит от места; +прошивка и RAM |
| **B. Хост → BMS** | i.MX95 + USB BT-донгл | Дисплей не меняется вообще; логирование на хосте; один source of truth | Нужен донгл (CSR8510 / RTL8761) и, желательно, удлинитель ближе к АКБ; тот же конфликт с телефоном |
| **C. CAN → хост** | хост через WeAct USB-CAN | 10 Гц, без запросов, без «занятого central», описание уже есть | Нужен адаптер и проводка к CAN-порту BMS; порт может быть занят инвертором |
| **D. Отдельный ESP32-мост** | ESP32 у АКБ | Радио рядом с BMS | +железо, +питание, дублирование функций дисплея |

**Рекомендация:**

- если на машине будет CAN — основным источником делать **C**, дисплей не трогать;
- если CAN нет или дисплей должен показывать напряжение сам — **A**;
- если хочется нулевых изменений прошивки дисплея — **B** (но с донглом и местом
  для него).

A и C не конфликтуют: CAN пассивный, BLE занимает только сам BMS.

## 5. План варианта A

### 5.1. Новые модули

```text
bms_ble.h/.cpp     — NimBLE central: scan, connect, subscribe, запросы, реконнект
jk_record.h/.cpp   — чистый декодер 300-байтового записи (без Arduino)
```

`jk_record` не зависит от Arduino, поэтому его можно прогнать на ПК на архивном
векторе как unit-тест. Это дешевле, чем ловить ошибку в offset’ах на железе.

### 5.2. Состояния

```text
OFF → SCAN → CONNECT → SUBSCRIBE → DEVICE_INFO (0x97) → READY (0x96 @ 1 Гц)
                       ↑                                   │
                       └────────── BACKOFF ←───────────────┘
```

- **SCAN**: 5 с, фильтр по сервису `FFE0` + MAC. По имени `JK` не фильтровать:
  дисплей рекламируется как `603134C60007081-00`.
- **CONNECT**: таймаут 5 с.
- **SUBSCRIBE**: `FFE1`, затем `0x97`, ждём `0x03` до 2 с.
- **READY**: раз в секунду `0x96`, ждём `0x02` до 2 с. Один запрос в полёте:
  следующий отправлять только после ответа или таймаута.
- 3 таймаута подряд → disconnect → BACKOFF: 5 с, 15 с, 30 с, далее 60 с.
- После реконнекта снова `0x97`, затем `0x96`.
- MTU: запросить 247. Connection interval: 30–50 мс, slave latency 4.

### 5.3. Сборка записей

```text
on_notify(data, len):
    if len == 4 and data == "AT\r\n": return
    buf += data
    while buf.len >= 300:
        i = find(buf, 55 AA EB 90)
        if i < 0: trim(buf, keep=3); return
        if i > 0: buf.erase(0, i)
        if buf.len < 300: return
        if sum(buf[0..298]) & 0xFF != buf[299]:
            buf.erase(0, 1); continue      // не выбрасывать весь буфер
        handle(buf[0..299]); buf.erase(0, 300)
```

Именно `erase(0, 1)` при ошибке CRC, а не «выбросить 320 байт»: иначе съедается
начало следующей записи.

### 5.4. Интеграция в UI

Сейчас `ui_update()` показывает напряжение только при `telem.valid` (хост прислал
хотя бы один кадр). Если дисплей работает только с BMS, это надо изменить:

| Что показываем | Источник |
|---|---|
| Напряжение | BMS, если свежая (<5 с); иначе хост |
| SOC / кольцо / % | BMS, если свежий; иначе хост |
| Чипы CRSF / WIFI / … | Только хост |
| GPS sats | Только хост |
| Одометр | Только хост |

«Свежесть» считать **для каждого источника отдельно**, иначе мигание низкого
заряда и приглушение будут срабатывать не от того источника.

Статусная строка — приоритет:

1. NOTIFY от хоста — всегда сверху;
2. `Link lost` — нет ни хоста, ни BMS;
3. `C2 link lost` — хост пропал, но BMS жив (напряжение свежее, чипы/одометр — нет);
4. `BMS lost` — хост жив, BMS был подключён и пропал;
5. пусто — всё в порядке.

`BMS lost` показывать только если BMS вообще был настроен и хотя бы раз
подключался, иначе на стенде без батареи будет вечное предупреждение.

### 5.5. Конфигурация (CONFIG, TLV)

Добавить тег `0x03` (тег `0x02` уже занят поворотом экрана):

```text
tag 0x03, len 1:  mode         0 = BMS выключен, 1 = включён
tag 0x03, len 7:  mode + MAC   6 байт MAC
```

Это позволяет:

- выключить BMS, когда нужно подключить телефонное приложение JK;
- сменить MAC без перепрошивки при замене батареи;
- не держать MAC в коде.

MAC по умолчанию — `A4:C1:38:05:47:C3`.

### 5.6. Опционально, фаза 2

Если данные BMS нужны хосту (логирование, аналитика) — добавить новый тип
сообщения **`0x9 BMS_STATUS`** от дисплея к хосту: напряжение, ток, SOC, T1/T2,
min/max ячейки, возраст данных. Сейчас единственный кадр display → host — `PONG`.
Изменение аддитивное, но потребует парсера и тестов в Rust-клиенте.

## 6. Оценка работ

| Этап | Дни |
|---|---|
| Спайк: NimBLE/Bluedroid, scan → connect → одна запись → напряжение в лог | 0.5–1 |
| Модуль `bms_ble` + декодер + реконнект + таймауты | 2–3 |
| Интеграция в UI/telemetry, CONFIG, документация | 1–1.5 |
| Тесты: дальность, конфликт с телефоном, 24-часовой soak | 1–2 |
| **Итого** | **4.5–7.5** |

Рабочий прототип — около недели. Надёжная версия со всеми состояниями и
документацией — ближе к 1.5 недели. Тип `0x9` — ещё +1.5–2 дня.

## 7. Риски

| Риск | Что делаем |
|---|---|
| Конфликт с приложением JK | Документируем: во время работы дисплея приложение не подключится. Даём CONFIG-режим «BMS off» для сервиса |
| BMS не рекламируется, потому что кто-то уже подключён | Ретраи с backoff, причина в лог; не мигать ошибкой на весь экран |
| Дальность / металл | Тест на месте; если плохо — вариант B (донгл на удлинителе ближе к АКБ) или CAN |
| RAM | Спайк с замером `free heap`; NimBLE вместо Bluedroid; при необходимости уменьшить буферы LVGL |
| Совместимость NimBLE-Arduino с Arduino core 3.3.12 | Проверяем на спайке; запасной вариант — встроенный Bluedroid BLE (тяжелее, но точно есть) |
| Другой вариант layout BMS (24-slot) | Санитарная проверка: пакет 10–100 В, SOC ≤ 100, сумма ячеек близка к пакету. Если не сходится — лог и отказ, а не «прыжок» на экране |
| Безопасность | PIN/пароль из device-info не логировать; мы только читаем |

Ориентировочная память: NimBLE — 50–80 КБ внутренней RAM и 250–350 КБ flash;
Bluedroid — заметно больше RAM. Flash не проблема (app 6 МБ), RAM надо мерить.

## 8. Открытые вопросы

1. **Есть ли на машине CAN-подключение к BMS?** Если да — зачем дублировать BLE?
2. **Где физически дисплей относительно АКБ?** Метры, стены, металл — от этого
   зависит, сработает ли A вообще.
3. **Можно ли отказаться от телефонного приложения JK во время работы?** Если
   нет — A не подходит как постоянный канал.
4. **Нужны ли данные BMS хосту** (логирование, аналитика)? Если да — тип `0x9`.
5. **Что показывать при потере BMS:** тихо перейти на напряжение от хоста
   (рекомендация) или явно писать `BMS lost`?
6. **MAC BMS:** зашивать в прошивку или конфигурировать через CONFIG? Рекомендация —
   CONFIG.

## 9. Что уже проверено, а что нет

Проверено:

- BMS в эфире: `A4:C1:38:05:47:C3`, имя `603134C60007081-00`, сервисы `FFE0`/`FEE7`,
  manufacturer data `0x0B65`, RSSI −70 dBm (с USB-BT-адаптера ПК, не с дисплея);
- архивный realtime-запись декодируется, напряжение и SOC извлекаются;
- CAN-канал для той же BMS описан и сверен с BLE в отдельных документах.

Не проверено:

- BLE central на прошивке дисплея (NimBLE/Bluedroid, сосуществование с USB CDC и LVGL);
- дальность и стабильность с места установки дисплея;
- расход RAM и flash;
- поведение при конфликте с телефонным приложением и при перезапуске BMS.
