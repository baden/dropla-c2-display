# Протокол связи с внешним устройством (v1)

Статус: **реализован для USB CDC.** Код: `firmware/c2_display/link.cpp` (парсер,
диспетчер), `telemetry.h` (модель данных), `ui.cpp` (отрисовка); тестовый клиент
для ПК — `tools/c2link.py`. UART и BLE подключаются к тому же парсеру позже,
на уровне «откуда пришли байты».

## 1. Какие каналы физически есть

| Канал | Что это | Годится для данных? | Ограничения |
|---|---|---|---|
| **USB Type-C** | нативный USB ESP32-S3 (GPIO19/20), режим USB-Serial/JTAG | **да**, полноценный | дисплей = USB-device, с другой стороны нужен host (ПК, Raspberry Pi/companion, телефон с OTG); при каждом ресете порт переоткрывается |
| **UART-гребёнка** | GND / 3V3 / TXD (GPIO43) / RXD (GPIO44), 3.3 В TTL | **да** | 3 провода; «UART Type-C» и гребёнка взаимоисключающие (по документации Waveshare) |
| **BLE 5.0** | только BLE, Classic нет | **да** | +60–80 КБ RAM, нужен реконнект/пейринг; 10–30 КБ/с реально |
| **Wi-Fi 2.4 ГГц** | AP или STA, TCP/UDP/MQTT/WebSocket | **да** | нужен SSID/пароль или фиксированная AP; самый большой расход энергии |

### Про USB подробно

В прошивке FQBN `USBMode=hwcdc,CDCOnBoot=cdc` — то есть `Serial` это **USB CDC**
(USB-Serial/JTAG периферия S3), а не UART-мост. Значит:

- это не «только питание и прошивка»: канал двунаправленный, `Serial.write()` /
  `Serial.read()` работают на любой «скорости» (для USB CDC baud — фикция);
- физически USB 2.0 Full-Speed 12 Мбит/с, практически ~0.5–1 МБ/с — с запасом
  для телеметрии 10–50 Гц;
- лог и бинарные кадры могут жить в одном потоке: кадры начинаются с `A5 5A`,
  текст лога — с печатных ASCII, парсер устройства/дисплея их не путает;
- GPIO19/20 также выведены на гребёнку (5V/GND/DN/DP) — можно подключить
  самодельный host-разъём без Type-C;
- подвох: дисплей не может быть USB-хостом «из коробки» (для этого нужен
  TinyUSB host + CDC-host, отдельная большая задача — не рекомендую).

### Про UART подробно

- `Serial1.begin(921600, SERIAL_8N1, 44 /*RX*/, 43 /*TX*/)` — UART1 на те же ноги,
  UART0/USB-CDC остаётся под лог, конфликта нет;
- 3.3 В TTL, без инверсии и без RS-232 уровней; обязательно общий GND;
- 3V3 на гребёнке — это выход, питать дисплей от устройства можно только если
  хватает тока (подсветка + экран ~100–150 мА), иначе отдельное питание;
- для связи «плата ↔ плата» на столе лучше 460800 или 921600: 18-байтный кадр
  на 115200 занимает ~1.6 мс, на 921600 — ~0.2 мс.

### Про BLE подробно

- ESP32-S3 умеет **только BLE 5.0**, Classic Bluetooth (SPP) — нет;
- самый практичный профиль — **NUS** (Nordic UART Service): две характеристики,
  RX/TX, поверх — тот же самый бинарный кадр, что и по проводу;
- клиенты есть готовые: nRF Connect, Web Bluetooth (Chrome), `bleak` (Python),
  Android/iOS;
- с MTU 247 и интервалом 15 мс реально ~10–30 КБ/с, задержка 15–50 мс — для
  телеметрии раз в несколько секунд огромный запас;
- ядро arduino-esp32 3.3.12 содержит `BLE` (Bluedroid). NimBLE (библиотека
  NimBLE-Arduino) легче по RAM, но ставится отдельно; начинать можно на Bluedroid.

## 2. Сравнение

| | USB CDC | UART | BLE | Wi-Fi |
|---|---|---|---|---|
| Проводов | 1 кабель | 3 | 0 | 0 |
| Дальность | 1–2 м | 0.3–2 м | 10–30 м | 50–100 м |
| Скорость (реально) | ~1 МБ/с | ~90 КБ/с @921600 | 10–30 КБ/с | 100+ КБ/с |
| Задержка | ~1 мс | ~0.2 мс | 15–50 мс | 5–30 мс |
| Питание дисплея | от кабеля | отдельное | отдельное | отдельное |
| Нужен host | да (ПК/RPi/телефон) | нет | нет | нет (роутер/AP) |
| Сложность | минимальная | минимальная | средняя | средняя |
| Когда выбирать | стенд, companion-компьютер | полётный контроллер, МК | телефон/пульт, без проводов | наземная станция в сети |

## 3. Архитектура

Один протокол — несколько транспортов. Разбор кадра живёт в одном месте и не
знает, откуда пришли байты:

```
              +-----------+
 USB CDC ---->|           |
 UART    ---->|  link.cpp |---> telemetry_t ---> ui_update()
 BLE NUS ---->|  (parser) |
              +-----------+
                    |
                    +--> PONG обратно в тот же транспорт
```

- транспортная обёртка умеет только «дай байты» / «отправь байты»;
- парсер один: поиск `A5 5A`, длина, CRC16, версия, тип сообщения;
- сейчас реализован USB CDC: `link_poll()` вызывается из `loop()` и читает
  `Serial` (в этой сборке `Serial` = USB CDC);
- добавление UART/BLE = новый источник байт, который кормит тот же `feed()`;
- симулятора больше нет: без кадров панель показывает прочерки (см. §7).

## 4. Формат кадра

Little-endian, без выравнивания, максимум 64 байта payload.

| Смещение | Размер | Поле | Описание |
|---|---|---|---|
| 0 | 2 | `magic` | `A5 5A` |
| 2 | 1 | `ver_type` | старший ниббл — версия протокола (1), младший — тип сообщения |
| 3 | 1 | `seq` | счётчик кадров, для диагностики потерь |
| 4 | 2 | `len` | длина payload |
| 6 | `len` | `payload` | см. ниже |
| 6+len | 2 | `crc16` | CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF) по байтам `[2 .. 6+len)` |

Свойства: парсер байтовый, ресинхронизируется по следующему `A5 5A`; битый кадр
просто отбрасывается (счётчик `rx_errors` в логе), счётчик `seq` показывает потери.

## 5. Сообщения

| Тип | Направление | Назначение |
|---|---|---|
| `0x1` TELEMETRY | устройство → дисплей | основные данные, раз в несколько секунд |
| `0x2` NOTIFY | устройство → дисплей | текстовое уведомление в строке статуса, по необходимости |
| `0x3` CONFIG | устройство → дисплей | настройки отображения (пока — единицы одометра) |
| `0x4` PING | устройство → дисплей | проверка связи |
| `0x81` PONG | дисплей → устройство | версия, uptime, число принятых кадров, `seq` запроса |

Тип `0x2` раньше в черновике назывался `TEXT`, `0x3` — `HELLO`; `HELLO` убран,
его роль выполняет `CONFIG`.

### 5.1 TELEMETRY (0x1), ровно 9 байт

| Смещение | Размер | Поле | Единицы |
|---|---|---|---|
| 0 | 2 | `voltage_cv` | сантивольты (5820 = 58.20 В) |
| 2 | 1 | `batt_pct` | 0…100, `255` = неизвестно (процент скрыт) |
| 3 | 1 | `flags` | бит0 CRSF, бит1 WIFI, бит2 STARLINK, бит3 LTE, бит4 VPN, бит5 GPS-fix, бит6–7 резерв |
| 4 | 1 | `sats` | число спутников (0 = нет фикса) |
| 5 | 4 | `odometer_dm` | дециметры (634 км = `6 340 000`) |

- GPS-плашка включается, если выставлен бит5 **или** `sats > 0`; при `sats > 0`
  на плашке пишется число спутников (`GPS 14`).
- Поля `status` в телеметрии больше нет — текст идёт отдельным сообщением `0x2`.
- Слишком короткий payload (< 9 байт) отбрасывается, лишние байты игнорируются
  (задел на расширение без смены версии).

### 5.2 NOTIFY (0x2)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `flags`: биты 0–1 — важность, бит2 — мигание, бит3 — скрыть через 5 с |
| 1 | 1 | `text_len` (0…80; в UI попадает максимум 63 символа) |
| 2 | `text_len` | текст UTF-8, без `\0` |

Важность: `0` debug, `1` info, `2` warning, `3` error.

| Важность | Цвет |
|---|---|
| debug | `#5B6B7C` (приглушённый серый) |
| info | `#8695A5` (серо-голубой) |
| warning | `#F59E0B` (янтарный) |
| error | `#EF4444` (красный) |

- `flashing` (бит2) — текст мигает всё время, пока показан (1 Гц, «выключение» =
  цвет фона, поэтому ничего не сдвигается);
- `hide after 5 seconds` (бит3) — сообщение исчезает через 5 с после приёма;
- **пустая строка** (`text_len = 0`) убирает сообщение немедленно (флаги при этом
  игнорируются);
- новое сообщение заменяет предыдущее и перезапускает таймеры;
- строка статуса под напряжением вмещает 300 px, дальше включается бегущая строка,
  так что длинный текст не обрезается.

### 5.3 CONFIG (0x3), TLV

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `count` — число элементов |
| 1 | … | элементы: `tag(1) len(1) value[len]` |

Известные теги:

| Тег | Длина | Значение |
|---|---|---|
| `0x01` | 1 | единицы одометра: `0` = км, `1` = мили |

- неизвестные теги **игнорируются** — старый дисплей не сломается от новых
  настроек, новые поля добавляются без смены версии протокола;
- шлётся один раз при старте и заново при изменении настроек;
- до первого CONFIG одометр считается в километрах.

### 5.4 PING (0x4) / PONG (0x81)

PING — пустой payload. Дисплей отвечает PONG, payload 10 байт:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | версия протокола (1) |
| 1 | 4 | `uptime_ms` |
| 5 | 4 | `rx_frames` — сколько кадров принято |
| 9 | 1 | `seq` из PING (эхо) |

PONG нужен для проверки кабеля/порта: `py tools/c2link.py --port COM4 ping`
печатает uptime и счётчик кадров. Дисплей сам никаких кадров не инициирует.

## 6. Примеры кадров (проверка парсера)

`seq` в примерах произвольный (у клиента он растёт с каждым кадром).

58.2 В, 95 %, все каналы + GPS-fix (`flags = 0x3F`), 14 спутников, 634 км:

```
A5 5A 11 01 09 00 BC 16 5F 3F 0E A0 BD 60 00 1D 59
```

(`0x11` = версия 1, TELEMETRY; `len = 0x0009`; CRC = `0x591D`.)

Уведомление `Starlink searching`, info, скрыть через 5 с (`flags = 0x09`):

```
A5 5A 12 02 14 00 09 12 53 74 61 72 6C 69 6E 6B 20
73 65 61 72 63 68 69 6E 67 6D 68
```

Очистка строки статуса (`flags = 0x01`, `text_len = 0`):

```
A5 5A 12 03 02 00 01 00 5F AF
```

CONFIG: единицы — мили (`count = 1`, тег `0x01`, длина 1, значение 1):

```
A5 5A 13 04 04 00 01 01 01 01 0C 61
```

PING:

```
A5 5A 14 05 00 00 66 BE
```

## 7. Поведение дисплея

### До первого кадра

- напряжение — прочерки `--.-` приглушённым цветом;
- процент скрыт совсем;
- кольцо пустое;
- все шесть плашек серые, у GPS без числа;
- одометр — `--` (единицы `km` до первого CONFIG);
- строка статуса пустая.

### Пока кадры идут

- значения обновляются при каждом TELEMETRY, UI перерисовывается 10 раз в секунду;
- низкий заряд (< 10 %) мигает красным;
- уведомление с `flashing` мигает, с `hide after 5 s` исчезает через 5 с.

### Потеря связи

- нет TELEMETRY **10 с** (`LINK_TIMEOUT_MS` в `telemetry.cpp`) → плашки гаснут
  в серый, значения и кольцо остаются последними, но тускнеют, в строке статуса
  появляется `Link lost` (янтарный);
- уведомление имеет приоритет над `Link lost`: если оно активно, показывается оно;
- кадры пошли снова → всё возвращается без перезагрузки и без повторной анимации;
- анимация включения играется один раз при подаче питания.

Почему 10 с: телеметрия штатно идёт «раз в несколько секунд», таймаут должен быть
заметно больше периода, иначе индикатор будет мигать на ровном месте. Меняется
одной константой.

## 8. Тестовый клиент

`tools/c2link.py` (Python 3 + `pyserial`) собирает кадры и пишет их в COM-порт;
логи дисплея печатает с префиксом `[dev]`.

```powershell
py tools/c2link.py --port COM4 demo                  # непрерывный демо-поток
py tools/c2link.py --port COM4 telemetry --voltage 58.2 --pct 95 --odo 634 `
                   --channels crsf,wifi,starlink,vpn --sats 14
py tools/c2link.py --port COM4 notify "Starlink searching" --severity info --hide
py tools/c2link.py --port COM4 notify "VPN down" --severity error --blink
py tools/c2link.py --port COM4 notify ""              # очистить строку
py tools/c2link.py --port COM4 config --odo mi
py tools/c2link.py --port COM4 ping
```

Особенности:

- клиент открывает порт, не удерживая DTR/RTS (иначе S3 может уйти в reset или
  download mode); если плата всё же перезагрузилась — это безвредно, кадры,
  отправленные во время анимации, уже примутся и покажутся после неё;
- `seq` растёт на единицу в каждом кадре;
- CRC в скрипте проверен на эталонном векторе `crc16("123456789") == 0x29B1`;
- скрипт не нужен прошивке — это только стенд для проверки.

## 10. Открытые вопросы

1. Кто на другом конце: Linux-companion (RPi/Jetson), полётный контроллер или
   телефон/пульт? От этого зависит, каким транспортом заниматься вторым.
2. Частота телеметрии: сейчас клиент шлёт раз в 2 с, таймаут 10 с — комфортно
   для 1–5 с; если период будет больше, таймаут надо увеличить.
3. Нужен ли набор плашек из конфига (сейчас шесть фиксированных: CRSF, WIFI,
   STARLINK, LTE, VPN, GPS) — под это уже готов TLV, добавим тег, когда решим.
4. Нужен ли обратный канал устройству, кроме PONG (например, подтверждение
   приёма NOTIFY или события кнопки питания)?
5. Может ли понадобиться нативный разбор CRSF или MAVLink вместо своего протокола?
