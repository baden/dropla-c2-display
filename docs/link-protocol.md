# Протокол связи с внешним устройством (черновик-предложение)

Статус: **предложение, код ещё не написан.** Дисплей сейчас работает на симуляторе
(`C2_SIMULATE 1`), внешнего канала нет.

## 1. Какие каналы физически есть

| Канал | Что это | Годится для данных? | Ограничения |
|---|---|---|---|
| **USB Type-C** | нативный USB ESP32-S3 (GPIO19/20), режим USB-Serial/JTAG | **да**, полноценный | дисплей = USB-device, с другой стороны нужен host (ПК, Raspberry Pi/companion, телефон с OTG); при каждом ресете порт переоткрывается |
| **UART-гребёнка** | GND / 3V3 / TXD (GPIO43) / RXD (GPIO44), 3.3 В TTL | **да** | 3 провода; «UART Type-C» и гребёнка взаимоисключающие (по документации Waveshare) |
| **BLE 5.0** | только BLE, Classic нет | **да** | +60–80 КБ RAM, нужен реконнект/пейринг; 10–30 КБ/с реально |
| **Wi-Fi 2.4 ГГц** | AP или STA, TCP/UDP/MQTT/WebSocket | **да** | нужен SSID/пароль или фиксированная AP; самый большой расход энергии |

### Про USB подробно

В прошивке FQBN `USBMode=hwcdc,CDCOnBoot=cdc` — то есть `Serial` это **USB CDC**
(USB-Serial/JTAG периферия S3), а не UART-мост. Значит:

- это не «только питание и прошивка»: канал двунаправленный, `Serial.write()` /
  `Serial.read()` работают на любой «скорости» (для USB CDC baud — фикция);
- физически USB 2.0 Full-Speed 12 Мбит/с, практически ~0.5–1 МБ/с — с запасом
  для телеметрии 10–50 Гц;
- лог и бинарные кадры могут жить в одном потоке: кадры начинаются с `A5 5A`,
  текст лога — с печатных ASCII, парсер устройства/дисплея их не путает;
- GPIO19/20 также выведены на гребёнку (5V/GND/DN/DP) — можно подключить
  самодельный host-разъём без Type-C;
- подвох: дисплей не может быть USB-хостом «из коробки» (для этого нужен
  TinyUSB host + CDC-host, отдельная большая задача — не рекомендую).

### Про UART подробно

- `Serial1.begin(921600, SERIAL_8N1, 44 /*RX*/, 43 /*TX*/)` — UART1 на те же ноги,
  UART0/USB-CDC остаётся под лог, конфликта нет;
- 3.3 В TTL, без инверсии и без RS-232 уровней; обязательно общий GND;
- 3V3 на гребёнке — это выход, питать дисплей от устройства можно только если
  хватает тока (подсветка + экран ~100–150 мА), иначе отдельное питание;
- для связи «плата ↔ плата» на столе лучше 460800 или 921600: 20-байтный кадр
  на 115200 занимает ~1.7 мс, на 921600 — ~0.2 мс.

### Про BLE подробно

- ESP32-S3 умеет **только BLE 5.0**, Classic Bluetooth (SPP) — нет;
- самый практичный профиль — **NUS** (Nordic UART Service): две характеристики,
  RX/TX, поверх — тот же самый бинарный кадр, что и по проводу;
- клиенты есть готовые: nRF Connect, Web Bluetooth (Chrome), `bleak` (Python),
  Android/iOS;
- с MTU 247 и интервалом 15 мс реально ~10–30 КБ/с, задержка 15–50 мс — для
  5–10 Гц телеметрии с огромным запасом;
- ядро arduino-esp32 3.3.12 содержит `BLE` (Bluedroid). NimBLE (библиотека
  NimBLE-Arduino) легче по RAM, но ставится отдельно; начинать можно на Bluedroid.

## 2. Сравнение

| | USB CDC | UART | BLE | Wi-Fi |
|---|---|---|---|---|
| Проводов | 1 кабель | 3 | 0 | 0 |
| Дальность | 1–2 м | 0.3–2 м | 10–30 м | 50–100 м |
| Скорость (реально) | ~1 МБ/с | ~90 КБ/с @921600 | 10–30 КБ/с | 100+ КБ/с |
| Задержка | ~1 мс | ~0.2 мс | 15–50 мс | 5–30 мс |
| Питание дисплея | от кабеля | отдельное | отдельное | отдельное |
| Нужен host | да (ПК/RPi/телефон) | нет | нет | нет (роутер/AP) |
| Сложность | минимальная | минимальная | средняя | средняя |
| Когда выбирать | стенд, companion-компьютер | полётный контроллер, МК | телефон/пульт, без проводов | наземная станция в сети |

## 3. Рекомендуемая архитектура

Один протокол — три транспорта. Логика разбора кадра живёт в одном месте и не
знает, откуда пришли байты:

```
              +-----------+     +-----------+
 USB CDC ---->| link_usb  |---->|           |
 UART    ---->| link_uart |---->|  link.cpp |---> telemetry_t ---> ui_update()
 BLE NUS ---->| link_ble  |---->|  (parser) |
              +-----------+     +-----------+
                                      |
                                      +--> ACK / heartbeat обратно в тот же транспорт
```

- каждая транспортная обёртка умеет только `read(bytes)` / `write(bytes)`;
- парсер один: поиск `A5 5A`, длина, CRC16, версия, тип сообщения;
- при старте выбирается транспорт (или все сразу, кто первый прислал валидный кадр);
- симулятор остаётся: `C2_SIMULATE 1` — демо, `0` — ждём кадры из канала.

## 4. Формат кадра

Little-endian, без выравнивания, максимум 64 байта payload.

| Смещение | Размер | Поле | Описание |
|---|---|---|---|
| 0 | 2 | `magic` | `A5 5A` |
| 2 | 1 | `ver_type` | старший ниббл — версия протокола (1), младший — тип сообщения |
| 3 | 1 | `seq` | счётчик кадров, для диагностики потерь |
| 4 | 2 | `len` | длина payload |
| 6 | `len` | `payload` | см. ниже |
| 6+len | 2 | `crc16` | CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF) по байтам `[2 .. 6+len)` |

Свойства: парсер ресинхронизируется по следующему `A5 5A`, битый кадр просто
отбрасывается, счётчик `seq` показывает потери.

## 5. Сообщения

| Тип | Направление | Назначение |
|---|---|---|
| `0x1` TELEMETRY | устройство → дисплей | основные данные, 5–20 Гц |
| `0x2` TEXT | устройство → дисплей | отдельная строка статуса (если не хочется пихать в телеметрию) |
| `0x3` HELLO | устройство → дисплей | имя/версия источника, версия протокола |
| `0x4` PING | устройство → дисплей | проверить связь |
| `0x81` PONG | дисплей → устройство | uptime дисплея, версия, число принятых кадров, `seq` последнего |
| `0x82` EVENT | дисплей → устройство | зарезервировано (тача нет, но могут быть события кнопки питания) |

### Payload TELEMETRY

| Смещение | Размер | Поле | Единицы |
|---|---|---|---|
| 0 | 2 | `voltage` | сантивольты (5820 = 58.20 В) |
| 2 | 1 | `batt_pct` | 0…100, `255` = неизвестно |
| 3 | 1 | `flags` | бит0 CRSF, бит1 WIFI, бит2 STARLINK, бит3 LTE, бит4 VPN, бит5 GPS-fix, бит6 авария АКБ, бит7 резерв |
| 4 | 1 | `sats` | число спутников (0 = нет фикса) |
| 5 | 4 | `odometer_dm` | дециметры (634 км = `6 340 000`) |
| 9 | 1 | `status_len` | длина текста, 0…47 |
| 10 | `status_len` | `status` | UTF-8, английский, без `\0` |

Итого 10 байт + текст; типичный кадр 30–40 байт. На 921600 это 0.3–0.4 мс,
на BLE — один пакет при MTU 247.

## 6. Пример кадра (для проверки парсера)

58.2 В, 95 %, все каналы включены, 14 спутников, 634 км, `Starlink searching`:

```
A5 5A 11 07 1C 00 BC 16 5F 3F 0E A0 BD 60 00 12
53 74 61 72 6C 69 6E 6B 20 73 65 61 72 63 68 69
6E 67 A1 E5
```

(`ver_type = 0x11` — версия 1, TELEMETRY; `len = 0x001C` = 28; CRC = `0xE5A1`.)

## 7. Поведение при потере связи

- нет валидных кадров **3 с** → в строке статуса `LINK LOST`, чипы серые,
  значения остаются последними (чтобы не мигало);
- нет кадров **10 с** → вместо цифр прочерки `--.-`;
- кадры пошли снова → плашка/строка восстанавливается без перезагрузки и без
  повторной анимации включения;
- анимация включения играется только один раз при подаче питания.

## 8. Этапы реализации

| Этап | Что делаем | Оценка |
|---|---|---|
| 1 | `link.h/.cpp` (парсер, CRC16, диспетчер) + `link_usb.cpp` + Python-скрипт, который шлёт кадры в COM-порт | 1–2 ч |
| 2 | UI: индикация `LINK LOST` / прочерки, `C2_SIMULATE 0` | 0.5 ч |
| 3 | `link_uart.cpp` (GPIO43/44, 921600) | 0.5 ч |
| 4 | `link_ble.cpp` (NUS, реконнект, имя устройства) | 2–3 ч |
| 5 | по желанию: Wi-Fi (TCP или WebSocket), MQTT | 2–3 ч |

Порядок сознательно такой: USB и UART дают рабочий стенд почти сразу, BLE
добавляется поверх уже отлаженного протокола, а не параллельно с ним.

## 9. Открытые вопросы

1. Что за «устройство» на другом конце: Linux-companion (RPi/Jetson), полётный
   контроллер/МК или телефон/пульт? От этого зависит, что делать первым.
2. Нужна ли беспроводная связь сразу или проводного стенда достаточно на первое время?
3. Частота обновления и максимальная длина статусного текста (сейчас UI держит 47 символов).
4. Нужен ли обратный канал (PONG/health) устройству, или достаточно, что дисплей просто рисует?
5. Может ли понадобиться нативный разбор CRSF или MAVLink вместо своего протокола?
